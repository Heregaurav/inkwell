# Part 3: Technology Stack Deep Dive

This section groups related technologies by architectural layer. Each drill is a project-specific question and answer. Some “why chosen” explanations are labeled as plausible rationale because a repository cannot establish the original author's intent.

## Frontend: React, Vite, Router, Zustand, Axios, CSS Modules

### What the code uses

- **React 18 / React DOM:** UI components and hooks. Routes and feature pages are wired in `frontend/src/App.jsx`; stateful content rendering is in `frontend/src/components/reader/BlockRenderer.jsx`.
- **Vite 4:** frontend dev server and build (`frontend/vite.config.js`, `frontend/package.json`). `VITE_API_URL` is read at build time by `frontend/src/utils/api.js`; no dev proxy is configured.
- **React Router 6:** client routes and route guards in `App.jsx`.
- **Zustand:** in-memory user/session status and guest-mode state in `store/authStore.js`; it stores no JWT.
- **Axios:** one API client with `withCredentials: true`; the browser sends the HttpOnly cookie, and 401 signals auth state clearing.
- **CSS Modules:** component/page-scoped styles. Lucide React, `react-hot-toast`, and `date-fns` are also declared/used. TipTap dependencies are declared but the inspected writer uses textareas rather than TipTap.

### Ten Interview Drills

1. **Question:** Why React for Inkwell? **Answer:** “The UI has reusable concepts—post cards, typed blocks, reader interactions, and page layouts—so component composition maps naturally to the product. I would still profile before optimizing renders.” **Concept:** declarative UI and component boundaries. **Follow-up:** “What can trigger a component render?” **Answer:** Its state, props, or consumed context/store updates; I’d identify the changing owner before memoizing.
2. **Question:** What is the role of Vite? **Answer:** “Vite serves the app during development and bundles it for production. In this repo, its config sets port 3000, but does not proxy `/api`; API routing in a container is instead handled by NGINX.” **Concept:** dev server versus production bundle. **Follow-up:** “How would you make local frontend-to-backend requests work?” **Answer:** Configure a Vite `/api` proxy or set `VITE_API_URL` to the backend origin and ensure CORS allows it.
3. **Question:** Why use React Router? **Answer:** “It maps URLs to pages such as `/post/:slug` and `/write/:id`, with route-level guards for login and guest access.” **Concept:** client-side routing is not backend authorization. **Follow-up:** “Can `ProtectedRoute` secure an API?” **Answer:** No; it is UX only. Express middleware must authenticate and authorize every protected operation.
4. **Question:** Why Zustand for auth state? **Answer:** “It keeps the user profile, guest mode, and loading status in memory; the JWT remains in an HttpOnly cookie managed by the browser.” **Concept:** client state versus server source of truth. **Follow-up:** “Can the store prove the cookie is valid?” **Answer:** No; `fetchMe` asks `/auth/me`, and the backend verifies it.
5. **Question:** What does the Axios client do for auth? **Answer:** “It sets `withCredentials: true`, so the browser sends the HttpOnly cookie; it does not attach a Bearer token. A 401 signals the app to clear in-memory auth.” **Concept:** cookie credentials and client session UX. **Follow-up:** “What should happen on a 403?” **Answer:** Keep the session; show access denied. 401 means missing/invalid authentication, 403 means authenticated but not permitted.
6. **Question:** What are CSS Modules buying here? **Answer:** “They scope class names to a component or page, reducing accidental style collisions without adding a runtime styling system.” **Concept:** CSS scoping and build transforms. **Follow-up:** “Do they prevent layout regressions?” **Answer:** No; responsive and visual tests and shared design tokens are still useful.
7. **Question:** What does React's reconciliation do? **Answer:** “React compares the next element tree with the current one and applies necessary DOM updates. In the block renderer, stable block IDs are used as keys.” **Concept:** virtual tree diff and identity. **Follow-up:** “Why are stable keys important?” **Answer:** They help React preserve the correct component identity when list items move; array indices can attach state to the wrong block after insertion/deletion.
8. **Question:** How would you reduce unnecessary rerenders? **Answer:** “First profile with React DevTools and find the changing state path. `BlockRenderer` maps each block; splitting state by block or memoizing stable children may help, but I wouldn’t add memoization without evidence.” **Concept:** render cost and state locality. **Follow-up:** “Would `useMemo` solve slow database requests?” **Answer:** No, it only memoizes a client-side calculation between renders; network and database latency need separate measurement.
9. **Question:** What happens to API URL configuration in Vite? **Answer:** “`import.meta.env.VITE_API_URL` is substituted at build time, so changing a runtime container environment variable alone may not change an already-built bundle.” **Concept:** build-time configuration. **Follow-up:** “How can one artifact move between environments?” **Answer:** Load runtime config from a served JSON/config endpoint or inject a generated config file at container startup.
10. **Question:** TipTap is in package.json; is it the editor? **Answer:** “Not in the inspected writer path. `WritePage` uses textareas and a block editor; the dependency is present but I would not claim the current UI uses TipTap.” **Concept:** dependency manifests versus executed code. **Follow-up:** “How do you decide whether to keep it?” **Answer:** Search imports/usage, check bundling and product plans, then remove only after validating no indirect or planned build use.”

## Backend: Node.js, Express, Middleware, REST

### What the code uses

Node.js 20 runs a CommonJS Express 4 service. `backend/src/index.js` creates one HTTP server, attaches Socket.IO, configures CORS/JSON/logging/rate limiting, mounts route modules, connects to MongoDB, seeds base topics, and only then listens. Async route handlers generally have local `try/catch`; no central error middleware or schema-validation layer is evident.

### Ten Interview Drills

1. **Question:** Why Node.js for this API? **Answer:** “The service is mainly I/O—MongoDB and external AI calls—so Node’s event loop can handle concurrent waits without a thread per request. CPU-heavy synchronous code can still block it.” **Concept:** event loop and nonblocking I/O. **Follow-up:** “Would an LLM call block the event loop?” **Answer:** Network waiting is asynchronous, but high-volume local parsing or CPU-heavy work can still consume the event loop; use worker threads or external workers if measured.
2. **Question:** What does Express middleware do here? **Answer:** “It composes cross-cutting request handling: CORS, body parsing, Morgan logging, global rate limiting, attaching `req.io`, then route dispatch.” **Concept:** ordered middleware pipeline. **Follow-up:** “What if an error occurs before a route?” **Answer:** Add centralized error middleware with the four-argument signature and ensure async errors reach it; currently many handlers catch errors themselves.
3. **Question:** Why REST for posts and votes? **Answer:** “The HTTP routes provide explicit operations and status codes, and REST requests persist state. Socket.IO only notifies connected readers about poll changes.” **Concept:** command/query API and transport separation. **Follow-up:** “Should a socket event replace the vote endpoint?” **Answer:** No; persist through an authenticated, validated command and publish an event after the durable write.
4. **Question:** How is API versioning handled? **Answer:** “All routes are mounted under `/api/v1`, giving a URL version boundary. I don’t see multiple supported versions or a deprecation policy.” **Concept:** backward-compatible evolution. **Follow-up:** “When introduce v2?” **Answer:** When a breaking contract change cannot be made compatibly; document, monitor usage, and sunset v1 deliberately.
5. **Question:** How does the server start? **Answer:** “It connects to MongoDB, runs `ensureBaseData`, then calls `server.listen`; connection/seeding failures log and exit.” **Concept:** startup dependency readiness. **Follow-up:** “Is `/health` sufficient for readiness?” **Answer:** It only returns `{status:'ok'}` and doesn't recheck MongoDB, so a dedicated readiness check should verify required dependencies and distinguish liveness from readiness.
6. **Question:** What does the 10 MB JSON limit protect? **Answer:** “It caps request body parsing memory for JSON requests. It is still generous and does not replace per-route field, array, or string limits.” **Concept:** resource bounds. **Follow-up:** “Could a valid 10 MB post still be harmful?” **Answer:** Yes; many blocks or expensive nested data can amplify database and processing costs, so validate structure and counts too.
7. **Question:** How do async handlers work? **Answer:** “Routes await Mongoose operations and return JSON. Many use `try/catch`; background AI starts with `.catch(console.error)` and is not awaited.” **Concept:** promise lifecycle and error propagation. **Follow-up:** “Why can unhandled promises be dangerous?” **Answer:** They can produce unobserved failure or process-level behavior; every asynchronous task needs explicit ownership, logging, retry policy, and state reporting.
8. **Question:** What does idempotency mean for an endpoint? **Answer:** “Repeating an operation should not unexpectedly duplicate its effect. GET is intended safe; toggle-style likes/bookmarks are not idempotent because a retry can undo the first action.” **Concept:** retries and idempotent commands. **Follow-up:** “How make publish retry-safe?” **Answer:** Use an idempotency key or client-generated operation ID with a unique constraint and return the original result for repeats.
9. **Question:** Is `DELETE /posts/:id` a hard delete? **Answer:** “No; it updates status to `archived`. The method expresses removal intent, while implementation is a soft archive. The UI’s ‘cannot be undone’ text is stronger than the code’s behavior.” **Concept:** API semantics and soft deletion. **Follow-up:** “How handle related records?” **Answer:** Define retention/cascade policy explicitly; archive may preserve comments/bookmarks but public queries must consistently exclude archived posts.
10. **Question:** What would you change in error handling? **Answer:** “I’d validate requests at the boundary, centralize error mapping, log internal detail with a request ID, and return stable public error codes rather than raw `err.message`.” **Concept:** error taxonomy and information disclosure. **Follow-up:** “What should a 500 response contain?” **Answer:** A generic message and correlation ID; stack traces and database/provider details belong in protected logs.”

## Data: MongoDB And Mongoose

### What the code uses

MongoDB is the datastore; Mongoose defines `User`, `Post`, `Comment`, `Topic`, and `QuizResponse` schemas. Post blocks and poll/quiz counts are embedded; authors, topics, responses, and quiz answers use ObjectId references. Index declarations appear in schema files. No explicit transaction/session use or migration framework is evident.

### Ten Interview Drills

1. **Question:** Why does MongoDB fit the block model? **Answer:** “Blocks have different shapes, and the reader often fetches a whole post. Embedding supports one-document reads and flexible content. It trades away some normalization and can make popular aggregates hot.” **Concept:** aggregate-oriented modeling. **Follow-up:** “Would arbitrary user content fit forever?” **Answer:** Not necessarily; enforce document and block limits, and move unbounded activity records out of the post.
2. **Question:** How do Mongoose schemas help? **Answer:** “They define field types, enums, defaults, references, and indexes, and run middleware such as reading-time calculation and password hashing.” **Concept:** application-layer ODM validation. **Follow-up:** “Are schema constraints enough against malformed writes?” **Answer:** Not if writes bypass Mongoose or validation isn't run; API validation and database-level invariants remain important.
3. **Question:** What is the role of a unique index? **Answer:** “User email/username, topic slug, post slug, and quiz response identity need uniqueness. The database index enforces the invariant under races.” **Concept:** constraint enforcement at the storage layer. **Follow-up:** “Why still handle duplicate-key errors?” **Answer:** A concurrent insert may lose the race; translate its database error into a deterministic conflict response.
4. **Question:** Why embed poll aggregates? **Answer:** “A poll result can be fetched with the post without another query. At high contention, a single post document becomes a hotspot and read-modify-save can lose updates.” **Concept:** read locality versus write contention. **Follow-up:** “What would you change?” **Answer:** Store individual votes with a unique voter key and maintain counts atomically or asynchronously.
5. **Question:** What do the indexes optimize? **Answer:** “The schema declares indexes on post status/date, author/date, topics/date, tags, text title/tags, slug, and comment post/parent/date. They align with observed query patterns but should be checked with `explain`.” **Concept:** index selectivity and write/storage cost. **Follow-up:** “Can more indexes always improve speed?” **Answer:** No; every index costs disk and write work, and the query planner may not use a poorly matched index.
6. **Question:** What is `populate` doing? **Answer:** “It resolves referenced IDs such as author and topic into selected fields, making response assembly convenient.” **Concept:** application-side reference resolution. **Follow-up:** “What can populate cost?” **Answer:** Extra queries and payload; select only needed fields and measure query count/latency, or use aggregation when appropriate.
7. **Question:** Does the project use transactions? **Answer:** “I found no explicit transaction/session use. Author follow updates two user documents; a partial failure can make reciprocal arrays inconsistent.” **Concept:** multi-document atomicity. **Follow-up:** “How repair it?” **Answer:** Use a transaction on a replica set or redesign a single authoritative follow edge and derive reciprocal counts/views.
8. **Question:** How does the reading-time hook work? **Answer:** “A `pre('save')` hook concatenates supported text fields, counts whitespace-separated words, and estimates minutes at 200 words/minute with a minimum of one.” **Concept:** derived data and lifecycle hooks. **Follow-up:** “What can make it stale or inaccurate?” **Answer:** Content omitted by the extraction expression, non-Latin tokenization, or updates that bypass `.save()`; centralize derivation and test representative scripts/languages.
9. **Question:** What consistency issue exists in quiz answers? **Answer:** “The response record is created, then aggregate counts are saved to the post. If the second write fails, the unique response exists but the displayed aggregate is stale.” **Concept:** dual writes and consistency. **Follow-up:** “How avoid it?” **Answer:** Transactionally write both, or derive counts from response records/materialize them with a repairable event pipeline.
10. **Question:** When migrate to PostgreSQL? **Answer:** “Not because one database is universally more scalable. I’d consider it if the domain needs stronger relational constraints, complex joins/reporting, and multi-row transactions, and if migration cost is justified by actual query and integrity requirements.” **Concept:** workload-driven database choice. **Follow-up:** “What would remain embedded?” **Answer:** Content blocks might remain JSONB if their shape is flexible, while accounts, relationships, votes, and transactional constraints could be normalized.”

## Identity: JWT And bcryptjs

### What the code uses

Registration creates a `User`; a Mongoose pre-save hook hashes `passwordHash` with bcryptjs cost 12. Login compares password using bcrypt. `generateToken` signs `{userId}` for seven days. Login/register set it as an `HttpOnly` `inkwell_session` cookie and return only the public user. `auth` verifies the cookie and loads the user; `optionalAuth` continues anonymously when missing/invalid. The frontend stores no JWT and removes any legacy `inkwell_token` key on initialization.

### Ten Interview Drills

1. **Question:** Why hash passwords with bcrypt? **Answer:** “Bcrypt is deliberately expensive and salts each hash, making offline guessing harder than storing a fast unsalted digest. The code uses work factor 12.” **Concept:** password hashing versus encryption. **Follow-up:** “Why not decrypt the password later?” **Answer:** Passwords should never be recoverable; compare a submitted password against the stored adaptive hash.
2. **Question:** What goes in the JWT? **Answer:** “Only a user ID is signed, and the token expires after seven days. The middleware still loads the current user from MongoDB on each protected request.” **Concept:** signed claims versus server-side session data. **Follow-up:** “Is this fully stateless?” **Answer:** No; verification is stateless cryptographically, but user lookup and revocation/disabled-account checks rely on the database.
3. **Question:** What does JWT signing provide? **Answer:** “Integrity and issuer authenticity under the secret; it does not encrypt the payload. Anyone holding the token can read its claims.” **Concept:** MAC/signature versus confidentiality. **Follow-up:** “Can I put private data in the payload?” **Answer:** No; keep it minimal and avoid secrets or sensitive profile data.
4. **Question:** What is the main JWT weakness here? **Answer:** “The middleware falls back to a predictable hard-coded secret. Production should fail startup if `JWT_SECRET` is missing and use secret management.” **Concept:** secure configuration and key rotation. **Follow-up:** “How rotate keys?” **Answer:** Support key IDs/overlap verification during migration, mint with the new key, then retire old verification keys after token expiry.
5. **Question:** Where does the browser store the token? **Answer:** “The browser stores the JWT in an HttpOnly `inkwell_session` cookie; JavaScript cannot read it, and Zustand keeps only the user profile.” **Concept:** browser storage threat model. **Follow-up:** “Does that eliminate XSS risk?” **Answer:** No; injected script can still act as the user even if it cannot exfiltrate the cookie.
6. **Question:** What is the difference between 401 and 403? **Answer:** “401 means authentication is missing or invalid; 403 means an authenticated identity lacks permission. The auth middleware returns 401; route-level ownership checks generally return 404 when not found/owned.” **Concept:** identity versus authorization. **Follow-up:** “Why might return 404 for unauthorized IDs?” **Answer:** To reduce resource-existence disclosure, but keep policy consistent and avoid hiding operational errors.
7. **Question:** How does optional auth behave? **Answer:** “It verifies a present token but swallows errors and continues without `req.user`, supporting public routes. That can make an invalid-token request behave as anonymous rather than explicitly fail.” **Concept:** anonymous access semantics. **Follow-up:** “When is that risky?” **Answer:** If the endpoint unexpectedly exposes private data or callers assume invalid credentials are rejected; define public/private query filters explicitly.
8. **Question:** Is six-character minimum password policy sufficient? **Answer:** “The route only checks length at least six, with no account lockout or dedicated login limiter evidenced. I’d use a stronger policy aligned with modern guidance, breached-password checks where appropriate, and rate-limit login attempts.” **Concept:** credential stuffing and password policy. **Follow-up:** “Would forced complexity rules solve credential stuffing?” **Answer:** No; throttling, MFA, breached-password screening, and monitoring address different attack paths.
9. **Question:** How revoke a JWT before expiry? **Answer:** “The current scheme has no explicit revocation list. Possible options are short lifetimes plus refresh-token rotation, a token-version field checked against the user, or a denylist with its own storage cost.” **Concept:** stateless token revocation trade-off. **Follow-up:** “What is the simplest approach?” **Answer:** Keep tokens short-lived and rotate refresh credentials securely; use a server-side version for immediate account-wide revocation if required.
10. **Question:** What happens on duplicate registration? **Answer:** “The route pre-checks email/username and returns 409 if found, while unique schema indexes are the actual race-safe constraint. A duplicate-key race is currently caught as generic 500.” **Concept:** TOCTOU and database constraints. **Follow-up:** “Fix?” **Answer:** Catch Mongo duplicate-key code and return a stable 409 without exposing raw database details.”

## Realtime: Socket.IO

### What the code uses

Socket.IO shares the HTTP server with Express. Clients join/leave `post:<postId>` rooms; a successful poll-vote route emits `poll-update` to that room. No Redis adapter or event persistence is configured. Comments remain REST-based.

### Ten Interview Drills

1. **Question:** What does Socket.IO add over REST? **Answer:** “It gives connected readers low-latency notifications without polling. REST still handles the authenticated vote and durable database update.” **Concept:** push notification versus state mutation. **Follow-up:** “What if the client is offline?” **Answer:** It misses the event; on reconnect, refetch canonical poll/post state.
2. **Question:** What is a room? **Answer:** “A server-managed group of sockets; Inkwell uses `post:<id>` to target readers of one post.” **Concept:** topic-based fanout. **Follow-up:** “Can any client join arbitrary IDs?” **Answer:** The current handler simply joins the requested room; production should validate the post and authorize visibility before joining.
3. **Question:** Is an emitted event durable? **Answer:** “No. The code emits after the MongoDB save, but there’s no event log or replay. The database remains the source of truth.” **Concept:** ephemeral pub/sub versus durable messaging. **Follow-up:** “How recover missed events?” **Answer:** Re-fetch state on reconnect or introduce a sequence/versioned durable event stream if replay matters.
4. **Question:** What changes with two backend replicas? **Answer:** “Rooms live in each process, so a socket connected to replica A won’t automatically receive a room event emitted by B.” **Concept:** distributed pub/sub. **Follow-up:** “Fix?” **Answer:** Add a Socket.IO adapter backed by Redis or another shared broker and test deployment/load-balancer behavior.
5. **Question:** Why use REST to vote and socket only to update UI? **Answer:** “The REST route can authenticate, validate, and persist before notifying others. Clients should not trust a client-originated broadcast as a durable vote.” **Concept:** command authority and event notification. **Follow-up:** “What if emit fails after save?” **Answer:** The vote remains persisted; clients reconcile by refetching. For guaranteed event publication use an outbox pattern.
6. **Question:** How avoid stale poll UI? **Answer:** “Treat updates as snapshots or versioned deltas and fetch canonical state after reconnect or detected gaps. The current client updates local vote counts from events and vote response.” **Concept:** eventual consistency and state reconciliation. **Follow-up:** “Why include version numbers?” **Answer:** They let a client detect reordered or missed updates and avoid applying stale state.
7. **Question:** How secure Socket.IO connections? **Answer:** “The inspected connection setup configures CORS but does not show auth middleware or room authorization. I’d authenticate the handshake, validate room membership, and re-check access on join.” **Concept:** transport-level authorization. **Follow-up:** “Is CORS authentication?” **Answer:** No; it constrains browser origins but does not establish user identity or prevent non-browser clients.
8. **Question:** Can events be duplicated? **Answer:** “Socket transports/retries and application behavior can produce duplicate notifications; clients should apply idempotent snapshots or event IDs.” **Concept:** at-least-once delivery. **Follow-up:** “How dedupe?” **Answer:** Include monotonically increasing post/poll version or event ID and ignore already-applied versions.
9. **Question:** What operational metrics matter? **Answer:** “Connected sockets, joins, event fanout, delivery errors, reconnects, room cardinality, and adapter health. No such instrumentation is evidenced.” **Concept:** observability of long-lived connections. **Follow-up:** “Why monitor room cardinality?” **Answer:** Unexpected growth can indicate clients not leaving rooms, high memory use, or abusive joins.
10. **Question:** Would you use WebSocket for comments? **Answer:** “Only if live comment updates are a product requirement. Today comments use REST; socket fanout adds connection state and cross-replica operational cost.” **Concept:** choose push only when interaction needs justify it. **Follow-up:** “Could Server-Sent Events work?” **Answer:** For server-to-client updates only, SSE may be simpler; client commands can remain REST.”

## AI Integration: OpenAI SDK And Groq-Compatible API

### What the code uses

The `openai` npm package constructs a client with Groq's OpenAI-compatible `baseURL`; configuration uses `GROQ_API_KEY`, `GROQ_MODEL` (default `openai/gpt-oss-20b`). `callAI` catches provider/JSON errors and returns `null`; deterministic heuristics generate fallbacks. Some endpoints are wired in the UI; others are API-only. AI can be unavailable without preventing core post persistence.

### Ten Interview Drills

1. **Question:** Which provider is actually configured? **Answer:** “The repository uses the OpenAI SDK with a Groq-compatible base URL and `GROQ_*` environment variables. The README’s GPT-4o wording doesn’t match the service implementation.” **Concept:** client library versus inference provider. **Follow-up:** “Why use an OpenAI-compatible API?” **Answer:** It can reduce client integration changes, but model behavior, limits, and response support still differ by provider.
2. **Question:** Why have a fallback? **Answer:** “Publishing and reader basics should still work if the provider key is absent or the request fails. `summarizeText` produces extractive heuristics; that is availability fallback, not equivalent AI quality.” **Concept:** graceful degradation. **Follow-up:** “How disclose fallback quality?” **Answer:** Track metadata status/provider and label generated versus fallback content so product behavior is transparent.
3. **Question:** How does `callAI` parse structured output? **Answer:** “It asks for JSON response format and attempts `JSON.parse`; parse failure returns null, letting callers use fallback logic.” **Concept:** probabilistic output behind deterministic contracts. **Follow-up:** “What’s missing?” **Answer:** Schema validation, explicit refusal handling, length validation, and tests against malformed/partial outputs.
4. **Question:** Why truncate post content sent to the model? **Answer:** “`generatePostMeta` passes at most 7,000 characters, limiting prompt size and provider cost. Truncation can omit conclusions or later examples.” **Concept:** context windows and lossy preprocessing. **Follow-up:** “Improve long-post summaries?” **Answer:** Chunk content and summarize hierarchically, or use retrieval/section summaries; compare quality and cost with representative tests.
5. **Question:** What is the risk of starting AI jobs in the API process? **Answer:** “They’re not durable and can consume provider capacity alongside requests. Process restart loses the job, and repeated edits can create duplicate work.” **Concept:** background job reliability. **Follow-up:** “First production change?” **Answer:** Durable queue with idempotent post/version jobs, concurrency limits, bounded retries, and persisted status.
6. **Question:** How prevent prompt injection? **Answer:** “User post text is untrusted input. Prompts should separate instructions and content, constrain tasks, validate output, and never grant the model tools or secrets it doesn’t need. The inspected service makes plain completion calls without tools.” **Concept:** untrusted data crossing instruction boundaries. **Follow-up:** “Can delimiters fully prevent injection?” **Answer:** No; they help clarify structure but must be combined with least privilege and output validation.
7. **Question:** How control AI costs? **Answer:** “Input truncation and token caps are present in calls, but no dedicated per-user cost/quota/concurrency controls are evident. Add request limits, usage tracking, caching keyed by content version, and provider budget alerts.” **Concept:** cost as a resource budget. **Follow-up:** “Would caching be safe?” **Answer:** Key by content hash, model, prompt version, and relevant context; invalidate when source changes and consider privacy/retention policy.
8. **Question:** How are AI output failures represented? **Answer:** “Provider errors are logged and returned as null; generation then uses a fallback or marks metadata failed on outer errors. The publish response doesn't expose a durable job ID.” **Concept:** failure state modeling. **Follow-up:** “What API should frontend poll?” **Answer:** A job status resource with state/version and retry semantics, or a post metadata endpoint that exposes pending/done/failed.
9. **Question:** Is AI-generated text trusted HTML? **Answer:** “No. It is model output and must be treated as untrusted text. The reader currently uses `dangerouslySetInnerHTML` for post HTML; that makes sanitization and safe rendering especially important.” **Concept:** output encoding and trust boundaries. **Follow-up:** “Best fix?” **Answer:** Render plain text/React nodes where formatting isn’t required; otherwise sanitize with a strict allowlist on a clearly defined trust boundary.
10. **Question:** What test strategy would you use? **Answer:** “Mock the provider, cover success, malformed JSON, timeout, missing key, and fallback outputs, then assert persisted metadata state and that publish does not wait for the provider.” **Concept:** deterministic testing of nondeterministic dependencies. **Follow-up:** “How evaluate quality?” **Answer:** Curated test corpus and human rubric or offline evaluator; separate quality evaluation from API correctness.”

## Deployment Layer: Docker, NGINX, Kubernetes/EKS, Terraform/AWS

### What the code uses

- Backend Dockerfile uses Node 20 Alpine, `npm ci`, non-root app user, `dumb-init`, port 5000.
- Frontend Dockerfile uses a Node build stage and NGINX 1.27 Alpine final stage, port 8080. NGINX serves SPA and proxies `/api/` and `/socket.io/`.
- Docker Compose runs MongoDB, backend, frontend with health checks and dependencies; MongoDB is published on host port 27017.
- Kubernetes manifests include two frontend and two backend replicas, services, probes, and ALB ingress. The combined manifest includes a single MongoDB pod/PVC and placeholder secrets.
- Terraform provisions AWS VPC/subnets/NAT, EKS, and ECR repositories. It does not provision a database service. EC2 path uses NGINX and PM2.

### Ten Interview Drills

1. **Question:** Why multi-stage Docker builds? **Answer:** “The frontend build needs Node/npm, but the runtime only needs NGINX and static assets. Multi-stage builds keep build tooling out of the serving image.” **Concept:** image layering and attack surface. **Follow-up:** “What should be pinned?” **Answer:** Base image digests/tags and lockfiles, with automated updates and vulnerability scanning.
2. **Question:** Why run containers as non-root? **Answer:** “The backend Dockerfile creates an app user and frontend NGINX runs as nginx, reducing privileges if the process is compromised.” **Concept:** least privilege. **Follow-up:** “Does that alone make the image secure?” **Answer:** No; minimize packages, secrets, capabilities, network access, and scan dependencies.
3. **Question:** What does NGINX do in the frontend container? **Answer:** “Serve built static files, fall back to index.html for SPA routes, and proxy API/socket traffic to the backend service in containerized deployment.” **Concept:** reverse proxy and SPA routing. **Follow-up:** “Why does local Vite still have issues?” **Answer:** The Vite config has no proxy; NGINX proxy only exists in the production-style container.
4. **Question:** What does Compose provide? **Answer:** “A local multi-container setup for Mongo, backend, and frontend with a Mongo health check and dependency conditions.” **Concept:** local orchestration, not high availability. **Follow-up:** “Is `depends_on` enough to guarantee dependency readiness?” **Answer:** Only with supported health condition semantics; apps should still retry connections because dependencies can fail later.
5. **Question:** What is a Kubernetes Deployment? **Answer:** “It declares desired pod replicas and lets the controller replace failed pods. The manifests specify two frontend and backend replicas.” **Concept:** reconciliation loop and declarative desired state. **Follow-up:** “Does two replicas guarantee availability?” **Answer:** No; placement, probes, capacity, database health, load balancer, and rollout strategy also matter.
6. **Question:** What are readiness and liveness probes for? **Answer:** “Readiness controls whether a pod receives traffic; liveness detects a stuck process and may restart it. The repo configures probes, but app `/health` is shallow.” **Concept:** health semantics. **Follow-up:** “Should liveness fail when Mongo is down?” **Answer:** Usually not automatically; otherwise all API pods may restart-loop. Readiness can reflect dependency availability; liveness should reflect process health.
7. **Question:** What does Terraform manage here? **Answer:** “The checked-in Terraform creates AWS network/EKS/ECR infrastructure. Kubernetes manifests and deployment scripts handle app resources; Terraform does not create MongoDB.” **Concept:** infrastructure as code boundaries. **Follow-up:** “Why remote state?” **Answer:** Team locking, shared state, and recovery; current state is local per inspected config, with an S3 backend commented out.
8. **Question:** What is the risk in the Kubernetes secret manifest? **Answer:** “The combined manifest contains placeholder/default configuration and must not be deployed unchanged.
